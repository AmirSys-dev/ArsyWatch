**Tarikh:** 14 Oktober 2026
**Fasa:** Firmware (Fasa 1)
**Hasil:** `pio run` berjaya. Firmware siap dan lulus semakan kontrak.

## Apa yang berlaku hari ini

Semalam server siap. Hari ni firmware. Satu fail, `main.cpp`, ~470 baris, dan
ia adalah bahagian yang paling mudah untuk nampak "betul" sedangkan ia tak betul.
Jadi saya tak percaya apa-apa yang saya tak ukur.

### Keputusan besar: RSSI tak ada dalam promiscuous mode

Ini yang saya hampir tersilap. Plan asal saya (dalam `.ino` stub) ialah:
sniff beacon, baca SSID/BSSID/RSSI dari frame tu, siap.

Masalahnya: **RSSI bukan sebahagian daripada bait frame 802.11.** Ia nilai
lapisan PHY — kekuatan isyarat yang diukur oleh radio, bukan data yang ditulis
ke dalam paket.

Saya semak betul-betul dalam header SDK yang terpasang, bukan dari ingatan:

```
user_interface.h:
    typedef void (* wifi_promiscuous_cb_t)(uint8 *buf, uint16 len);
```

Itu sahaja. Dua argumen: buffer dan panjang. Tiada RSSI.

Pada ESP32 ada `wifi_promiscuous_pkt_t` dengan medan `rx_ctrl.rssi`. Saya cari
seluruh SDK ESP8266 — **struktur tu tak ada langsung**. Ia ESP32 sahaja. Kalau
saya tulis kod seolah-olah `rx_ctrl` wujud, ia tak akan compile, atau lebih
teruk, saya akan reka nombor.

Dan kontrak (`docs/api.md` §1.2) **wajibkan** `rssi` integer dalam −100..0.

Jadi macam mana? Satu-satunya sumber RSSI sebenar pada cip ini ialah **managed
scan** (`WiFi.RSSI(i)`). Keputusan saya:

- Senarai AP datang dari managed scan (dapat SSID, BSSID, RSSI, channel, enc).
- Beacon parsing dari promiscuous mode **melengkapkan** ia: SSID sebenar untuk
  AP tersembunyi, dan pengesanan WPA3 yang managed scan tak nampak.
- Saya **tak pernah reka RSSI**. AP tanpa isyarat terukur tak dihantar.

Ini bukan kompromi yang saya suka, tapi ia satu-satunya cara yang jujur untuk
dapat RSSI sebenar pada hardware ini. Kalau saya tunjuk nombor yang saya tak
ukur, itu pembohongan data.

### Stream JSON, bukan satu String besar

Kontrak minta stream. Heap cuma ~40KB. Kalau saya bina satu `String` untuk 20 AP
+ 200 MAC, saya akan pecahkan heap.

Saya guna **HTTP chunked transfer-encoding**: setiap serpihan JSON ditulis
sebagai chunk sendiri. Puncak memori kekal beberapa ratus bait walau berapa
banyak AP. Bonus: saya tak perlu kira `Content-Length` di hadapan, jadi satu
kelas bug hilang terus.

### Buffer TLS

Default BearSSL ialah 16KB receive + 512 xmit ≈ 17KB. Itu hampir separuh heap
saya. Response ingest < 1KB, jadi saya kecilkan kepada 2048/512 ≈ 2.5KB.
`setBufferSizes` clamp kepada lantai 512.

### Pin sijil, bukan `setInsecure()`

`client.setFingerprint(API_CERT_FINGERPRINT)` — SHA-1 20 bait. Kalau fingerprint
salah atau masih placeholder, handshake **gagal tertutup**. Tiada data dihantar.
Ini penting: `setInsecure()` akan "berjaya" tapi membunuh seluruh model privasi
projek ni.

## Benda yang makan masa

**1. Amaran `\` di hujung komen `//`**

Saya tulis contoh openssl dalam komen:

```c
//   openssl s_client ... </dev/null 2>/dev/null \
//     | openssl x509 ...
```

Backslash di hujung baris bermakna **baris berikutnya disambung** — jadi baris
`| openssl x509` ditelan jadi sebahagian komen. GCC keluar
`-Wcomment: multi-line comment`. Bukan fatal, tapi ia tanda saya tak fikir.
Dibetulkan.

**2. `#warning` yang saya sendiri tulis**

Saya letak `#warning` untuk beritahu operator bila guna `secrets.example.h`.
Bagus niatnya, tapi ia bermakna clone baru **selalu** keluar amaran. Tukar
kepada notis runtime dalam `setup()`. Kini clone baru compile dengan sifar
amaran.

**3. Panggilan SDK dalam ISR**

Callback promiscuous berjalan dalam konteks interrupt. Saya mula-mula panggil
`wifi_get_channel()` di dalamnya untuk label frame tanpa DS IE. Itu panggilan
SDK dari ISR — tak selamat. Saya tukar kepada `volatile uint8_t g_currentChannel`
yang main loop tulis sebelum setiap hop. ISR cuma baca bait.

## Cara saya buktikan ia betul (bukan andaikan)

1. **`pio run`** — build bersih. RAM 40.6%, Flash 36.9%.
2. **Validator sebenar server.** Saya salin logik `jsonEscape()` dari firmware ke
   Node, bina payload tepat seperti yang di-stream, dan hantar melalui
   `validateIngest()` server. Lulus. Termasuk SSID dengan `"` dan `\` — round-trip
   byte-perfect.
3. **End-to-end hidup.** Saya naikkan server sebenar dan POST payload firmware
   yang sama ke `/api/v1/ingest`. **HTTP 201.** Response padan `docs/api.md` §1.3
   tepat: `scan_id`, `aps_stored`, `macs_stored`, `new_aps`, `reboot`.
4. **Had kontrak.** 21 AP → ditolak. 201 MAC → ditolak. Sempadan rssi −100/0 dan
   channel 1/14 → diterima.

Saya tak boleh flash cip dari sini (tiada hardware), jadi perkara yang tinggal
tak terbukti ialah **promiscuous mode sebenar pada board**. Itu risiko yang saya
nyatakan awal, dan ia kekal risiko sehingga ada cip di tangan.
